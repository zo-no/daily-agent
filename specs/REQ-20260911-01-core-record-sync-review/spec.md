## 目标与范围

本规格把 Log Note 的核心“记录与同步”拆成四个必须按顺序讨论和验收的阶段，避免一次性设计完整同步系统。本轮只规划第一阶段，并为后续阶段锁定数据契约和边界；不提前实现云端行为。

阶段边界：

1. **本地同步与恢复**：设备内、账号内的数据一致性、异常恢复、导入导出和重启后恢复。
2. **云端保存本地**：本地状态向云端保存，云端作为可恢复副本；云端读取不能直接覆盖本地。
3. **云端冲突合并**：多个设备或写入者产生不同版本时，保护双方数据并形成明确合并结果。
4. **双向历史回溯**：合并后的本地替换可撤销、可查看；云端保留可查询和恢复的版本历史。

本包原先先建立第一阶段的现状、契约、数据模型、目录方案和验收计划；根据已确认的 Clarifications，当前执行切片进一步包含步骤一的行为保持迁移：允许整理目录、转换为 TypeScript、拆分职责和更新引用，但不改变本地序列化格式、`commitData`/`replaceData` 语义或云端运行语义。步骤二数据流梳理和步骤三本地保存机制优化不进入本轮 plan/tasks。AI、日历、图片云同步和自动语义合并均不在本包范围内。

## 当前实现基线（待共同确认）

- 首页及编辑器通过 `LogNoteDataProvider` 暴露 `commitData` 作为文字状态的规范写入口。
- 设置页的备份导入/恢复当前还通过公开的 `replaceData` 写入；它是本轮必须审计的第二个状态写入者，不能在方案中假设不存在。
- `commitData` 先更新当前账号的本地缓存，再标记 dirty，并触发延迟同步；无账号时保持 local-only。
- 云文档路径使用账号身份、文档 revision 和 CAS；冲突时进入 conflict，不覆盖较新远端。
- 当前同时存在 legacy 文档同步与 record/plan 增量 stream、outbox、cursor、item version 和冲突状态，需要确认两者的权威关系与收敛计划。
- 新设备云端读取失败时，当前实现区分 load-error/offline，并保留本地可用状态；该行为需要以用户可理解的产品文案和重试规则确认。
- 工作树已有并行未提交修改，涉及 Provider、account-sync、测试和 Supabase migration；本规格不授权覆盖或清理这些改动。

## 本轮规划边界

第一阶段的实现目标是“本地明确保存、可靠读取、失败保护和备份恢复”。它继续复用当前 `commitData` 主路径和 `AccountDataPayload` 业务字段，不改变记录语义，不把云端状态引入本地成功条件。

以下内容只作为后续对齐约束，不能在第一阶段顺手实现：云端副本写入、云端覆盖策略、跨设备冲突合并、本地或云端历史 UI、增量流主路径选择、图片 Blob 云同步。

本阶段按项目 Constitution 的全局分层、社区 Store、单一持久化写入和核心链路讨论门禁执行；本
feature 只记录这些全局规则在本地恢复场景中的具体落点，不把它们重新定义为 feature 专属制度。

## Core-Chain Change Contract

本 feature 触及记录保存、恢复、备份和持久化边界，按项目 Constitution 的全局门禁记录本次具体落点：

- **Canonical path**：普通记录/编辑/删除继续沿用 `LogNoteDataProvider.commitData`，本切片只把其依赖迁移到 `application/account-data` 与 `infrastructure/local`；整包恢复的 `replaceData` 语义不在本切片改变。
- **Reuse**：复用现有 `AccountDataPayload`、`normalizeState/restoreState`、账号 generation、localStorage/IndexedDB 账号隔离和备份格式。
- **Replacement / deletion**：迁移调用方后删除承载核心恢复/同步的旧 `src/lib` 入口；未满足调用方、测试和结构检查条件前不删除。
- **State writers**：当前可见 `commitData` 与设置页 `replaceData`；本阶段目标是一个受控本地持久化边界。
- **Public contract**：本切片先建立纯 TypeScript `AccountDataPayload` 和现有版本迁移类型；`LocalSnapshotEnvelope`、恢复结果细节和本地校验规则留到步骤三讨论，云端 revision/cursor 仅做对齐。
- **Invariants**：本地成功先于云端、账号隔离、失败不以空状态覆盖、原始记录可恢复、旧备份可读、附件不进入文字云同步。
- **Verification**：本地保存/读取/损坏/恢复/账号隔离/备份回归，结构引用检查和最终 `npm run check`；本阶段无真实云端证据。
- **Unresolved evidence**：本地封套是否启用、有限快照和多标签页范围、`replaceData` 最终命令语义、Store ADR 门槛仍待产品负责人确认；这些不阻塞本切片。
- **Discussion status**：步骤一的分层方案已确认；后续本地保存行为仍需继续讨论。

## User Scenarios & Testing

### User Story 1 - 本地数据同步与恢复（Priority: P1）

用户在同一设备和账号内记录、编辑、删除后，即使应用重启、浏览器异常或本地写入中断，也能恢复到最近一次明确保存的本地状态。

**Independent Test**: 不连接云端，连续执行记录操作并模拟刷新、重启、异常中断和备份恢复，确认数据完整且账号不串。

### User Story 2 - 云端保存本地副本（Priority: P1）

用户明确知道本地数据何时已保存、何时已上传；云端读取失败或存在旧版本时，本地内容仍保持为当前工作版本。

**Independent Test**: 模拟首次上传、断网、云端旧版本、云端读取失败和重新登录，确认本地不被云端静默替换。

### User Story 3 - 云端保存冲突合并（Priority: P1）

多个设备同时保存时，系统保留冲突双方，展示可理解的差异，并生成一次明确的合并结果。

**Independent Test**: 两个独立会话修改同一记录或文档，验证旧版本保护、冲突证据、合并确认和再次保存。

### User Story 4 - 本地与云端历史回溯（Priority: P2）

用户在合并或覆盖后可以回看、撤销或恢复本地历史，也可以查看和恢复云端历史版本。

**Independent Test**: 连续生成多个本地和云端版本，执行合并、撤销、恢复和再次同步，确认版本来源、时间和内容可区分。

### Edge Cases

- 本地写入中断、缓存损坏、导入文件损坏、恢复过程中再次退出。
- 本地有未上传变更，云端只有旧版本、空版本或读取失败。
- 两台设备同时编辑、删除与编辑并发、冲突处理期间远端再次变化。
- 合并后本地撤销、云端回滚、历史版本过多、账号切换和权限失效。
- 图片附件只存在本地时，本地与云端文字版本如何关联。

## Requirements

### Functional Requirements

- **FR-001**: 系统 MUST 将本地明确保存作为第一成功条件，第一阶段不依赖云端。
- **FR-002**: 系统 MUST 支持本地状态在重启、异常中断和备份恢复后的完整恢复，并保持账号隔离。
- **FR-003**: 第一阶段普通记录、编辑和删除 MUST 继续复用 `commitData` 规范入口；备份导入和恢复的受控入口 MUST 与其共享同一个底层本地持久化边界。
- **FR-004**: 第二阶段 MUST 将云端定义为本地状态的保存副本；云端读取失败、为空或版本较旧时 MUST 不得静默覆盖本地。
- **FR-005**: 系统 MUST 明确区分本地已保存、云端保存中、云端已保存和云端保存失败。
- **FR-006**: 第三阶段 MUST 使用可验证版本保护云端写入；冲突时保留本地和云端内容，不得静默丢弃任一方。
- **FR-007**: 合并 MUST 是可检查、可确认、可重复验证的明确结果，并绑定产生合并时的双方版本。
- **FR-008**: 第四阶段 MUST 保留合并前后的本地历史，使用户可以查看、撤销或恢复。
- **FR-009**: 云端 MUST 保留可查询的版本历史，并支持在权限和版本校验通过后恢复指定版本。
- **FR-010**: 本地历史和云端历史 MUST 标明来源、版本、时间和恢复结果，不能混为一个不可解释的时间线。
- **FR-011**: 图片 Blob 不因本规格进入云端文字同步；本地附件与文字历史必须保持账号隔离和备份兼容。
- **FR-012**: 第一阶段 MUST 明确收敛 `replaceData` 与 `commitData` 的关系：备份导入和恢复可以是不同语义的命令，但最终只能由一个受控本地写入者完成持久化；不得让 `replaceData` 继续作为未审计的平行公开写入口。

### Key Entities

- **本地账号状态**：当前账号的记录、计划、结构和设置，以及本地可用版本。
- **业务数据契约**：前后端都可读取的纯 TypeScript `AccountDataPayload` 及实体 schema；不包含运行时状态和存储元数据。
- **本地保存封套**：本地版本、操作标识、保存时间和完整性校验等恢复元数据；不进入业务 payload。
- **云端账号文档**：账号范围内的文字状态及其服务端版本。
- **同步元数据**：最近确认的远端版本、内容指纹、设备信息和同步状态。
- **增量同步流**：按记录或计划组织的游标、基础版本、条目版本、outbox 和冲突集合。
- **冲突决策**：绑定账号、实体、基础版本和用户选择的待应用结果。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 在离线测试中，100% 的记录创建、编辑和删除操作在本地成功完成，且重启后可读回。
- **SC-002**: 在网络失败、服务端错误和鉴权失效测试中，0 次出现本地已保存记录被静默删除或被空状态覆盖。
- **SC-003**: 在并发版本测试中，100% 的旧版本写入被拒绝或转入冲突，0 次覆盖较新远端内容。
- **SC-004**: 用户能够从界面明确区分本地保存成功与云端同步成功；相关状态在聚焦浏览器回归中全部有覆盖。
- **SC-005**: 第一阶段方案能明确列出本地保存点、恢复入口、失败保护、备份证据和后续云端排除项，并可由 review 逐项确认。

## Assumptions

- 现有 Supabase Auth、账号级云文档和 revision/CAS 只作为后续对齐事实；第一阶段不调用云端。
- 记录与计划增量 stream 是当前正在演进的实现事实，是否成为唯一主路径需要 review 后决定。
- 第一阶段优先保证可靠保存、读取、失败保护和备份恢复；冲突保护只保留契约边界，不实现云端冲突算法。
- 图片附件继续使用本地 IndexedDB 与备份契约，不因文字同步 review 扩大为云 Blob 同步。
- 本规格是讨论基线；`plan.md` 是本轮方案产物，只有产品负责人 review 后才可生成 tasks 并进入实现。
