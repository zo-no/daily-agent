# Research: 静态资源缓存优先

## Decision: 仅对版本化构建资源采用缓存优先

**Rationale**: 这类资源随应用构建更新，内容不含账号数据；重复请求既无新鲜度价值，也会降低实际缓存命中。现有离线壳已对路由、公开静态素材和 API/RSC/认证边界分别处理，因此该分支可以小而独立。

**Alternatives considered**:

- 所有页面缓存优先：拒绝。页面可能随着认证或发布状态变化，且离线壳在同域名下共享，不能扩大动态页面的缓存边界。
- 页面 stale-while-revalidate：暂不采用。它能改善再次打开，但需要先确认页面响应没有账号内容、更新语义和 query 兼容性；超出“提高构建资源命中率”的最小范围。
- 引入缓存框架：拒绝。现有离线壳足以实现该分支，新增依赖会扩大升级、审计和维护面。

## Decision: 以新的离线壳版本隔离策略

**Rationale**: 当前同一缓存中存有上一构建的运行时资源；缓存优先前必须更换壳版本，才不会让更新后的页面从旧壳取到旧构建文件。

**Alternatives considered**:

- 保持现有版本：拒绝。旧的运行时条目会与新策略混用，不能证明构建一致性。
- 按单个资源追加版本：拒绝。构建路径已承担版本化职责，额外维护资源级版本增加复杂度。

## Decision: 用受控单元测试证明“命中不触网”

**Rationale**: 现有生产 PWA 回归可证明离线后备、边界与更新，但网络优先在网络故障时也会回退缓存，不能单独证明在线缓存命中。受控 Service Worker 环境可以精确断言缓存命中时网络调用次数为零，并与生产 PWA 回归互补。

**Alternatives considered**:

- 只检查缓存中是否存在资源：拒绝。存在并不能证明在线重复访问会优先读取它。
- 添加运行时命中遥测：拒绝。会引入额外数据和隐私/运维边界，当前需求不需要。
