# 纪律红线（始终生效）

## 1. 范围控制
- 在写代码前必须明确"我要改什么、不改什么"
- Bugfix 中禁止无关重构。修 bug 就只修 bug；但如果当前修复必须替换、合并或删除造成问题的旧逻辑，这些变更属于当前范围，不能为了“最小 diff”继续保留重复主路径。
- 不在任务范围内的改动，记录但不执行
- "顺手改了"= 范围蔓延 = 错误

## 2. 最小改动
- 用最小的**语义差异**达成目标，而不是机械追求最少字符或最少行
- 先复用当前 canonical path；若旧实现与本次目标冲突，先替换、合并或删除，再补上确实缺失的语义
- 同一行为默认只保留一条活跃实现路径（one behavior → one canonical path）
- 不改风格、不重命名、不提取函数——除非这正是任务目标
- 改动量超过预估 2 倍时，停下来确认

## 2.1 变更前账本
- 写明：目标、canonical path、复用位置、删除/替换位置、必须保留的旧逻辑、确实需要新增的文件/函数/状态、公共契约、不变量和验证命令
- 每一处新增语义都要说明为什么不能由复用、替换或删除完成
- 账本不是要求扩大范围；它是防止“只增不减”和重复实现的检查点

## 3. 计划纪律
- 探索最多 2 轮。信息不完美也要动手。
- Todo list 写好后锁定。只允许追加，不允许重写。
- "让我重新想想" = 重规划警报。执行现有计划。

## 4. 失败处理
- 同一个问题最多尝试修复 3 次
- 每次重试前必须说明和上次的**本质区别**
- 链式错误（A→B→C→A）立即停止
- 3 次失败后：revert → 写报告 → 求助。不允许第 4 次。
- 禁止 `as any`、`@ts-ignore`、删测试等绕过手段

## 5. 类型安全
- 绝不使用 `as any`、`@ts-ignore`、`@ts-expect-error`
- 绝不使用空 catch 块 `catch(e) {}`
- 绝不删除失败的测试来"通过"
