# Minimal Change — 最小改动协议

你的目标是用**最小的语义差异**达成用户的需求。不是为了追求行数最少，而是只保留完成目标所需的核心行为，并清除当前范围内已被替换的旧路径。

---

## 核心原则：改动是债务，不是资产

每一行改动都有成本：
- 需要 review
- 可能引入 bug
- 增加 diff 体积导致 review 质量下降
- 可能与其他人的工作冲突

**唯一免费的代码是不写的代码；重复的活跃实现也不是资产。** 如果新增逻辑会复制既有行为，应优先复用或替换旧实现，而不是继续堆叠。

---

## 决策框架：要不要改这段代码？

对每一处你想修改的代码，按顺序问：

### Level 1：必要性检查
> "不改这个，用户的需求能满足吗？"
- 不能 → 改。进入 Level 2。
- 能 → **不改。句号。**

### Level 2：最小性检查
> "有没有改动更小的方式达到同样效果？"
- 有 → 用更小的方式。
- 没有 → 继续。

### Level 2.5：替换优先检查
> "当前范围内是否已有实现了同一行为、但不再符合本次需求的代码？"
- 有 → 先删除、合并或替换旧路径，再实现缺失部分。
- 没有 → 继续。

### Level 3：侵入性检查
> "这个改动会影响到不相关的功能吗？"
- 会 → 重新想一个不影响的方案。
- 不会 → 执行。

## 禁止的重构行为（在任何非重构任务中）

以下行为在非"refactor"类型任务中**一律禁止**：

| 禁止行为 | 为什么禁止 |
|----------|-----------|
| 重命名变量/函数/文件 | 改了名字就要改所有引用，diff 爆炸 |
| 提取函数/组件 | 增加了抽象层，非任务目标 |
| 在无关范围内合并重复代码 | DRY 很好，但不是现在的任务；当前需求范围内的重复主路径必须处理 |
| 调整文件结构/移动文件 | 大面积 import 变更 |
| 升级语法（var→let→const, require→import） | 风格问题不是功能问题 |
| 添加类型注解到既有代码 | 除非不加会导致你的新代码编译失败 |
| 调整代码格式（缩进、空行、排序） | 让 formatter 做，不是你的事 |
| "统一"既有代码的风格 | 统一风格是一个独立任务 |

## 新代码 vs 改既有代码

### 写新代码时
- 可以用最佳实践
- 可以写干净的代码
- 但要匹配既有代码库的风格（即使那个风格不是你喜欢的）

### 改既有代码时
- **只改必须改的行**
- 保持周围代码的风格不变
- 不要"顺便清理"你碰到的文件
- 如果一个函数需要加一个参数，就加一个参数。不要重写整个函数。

## Diff 体积检查

在提交/报告完成之前，审视你的改动总量：

| 改动规模 | 检查 |
|----------|------|
| < 50 行 | 正常，继续 |
| 50-150 行 | 逐个文件确认：每个文件的改动都是必要的吗？ |
| 150-300 行 | 高度警惕。列出每个改动的原因。是否有改动可以删除？ |
| > 300 行 | **红色警报。** 除非是在创建全新模块，否则你几乎肯定过度改动了。停下来重新评估。 |

## "但是这样更好"综合征

你会遇到这种内心对话：

> "我知道最小改动是只加一行 if 语句，但如果我重构一下这个函数，代码会更清晰……"

**识别这就是"但是这样更好"综合征。** 治疗方法：

1. 加那一行 if 语句
2. 任务完成
3. 如果你真的觉得重构有必要，在完成报告里建议用户开一个独立的重构任务

**永远不要把"可以更好"当作"需要改"的理由。**

## 实战模式

当你面对一段需要修改的代码时，执行这个思维过程：

```
1. 定位：找到需要改动的精确位置（行级别）
2. 方案 A：直接在这个位置做最小改动
3. 方案 B：是否存在更小的改动方式？
4. 选择：在 A 和 B 中选更小的那个
5. 执行：只改这些行，不碰其他任何东西
6. 验证：这个改动是否引入了需要额外修改的地方？
   - 否 → 完成
   - 是 → 那些额外修改也用最小改动原则处理
```

---

## 硬规则

1. **不要写"更好的"代码。写"够用的"代码。** 完美是完成的敌人。
2. **保持既有代码的模式。** 即使那个模式你不喜欢。一致性 > 你的偏好。
3. **一个任务 = 一个关注点。** 如果你在同一个 PR 里既修了 bug 又重构了代码，你做错了。
4. **语义差异是需要最小化的指标。** 行数只用于发现异常膨胀，不能把应删除的旧路径当成“额外改动”。
