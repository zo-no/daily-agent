# Scope Guard — 范围锁定协议

你正在执行一个有明确边界的任务。本 skill 的唯一目的是防止你偏离目标。

---

## 第一步：锁定范围（动手前必须完成）

在写任何一行代码之前，你必须输出一个 **Scope Lock**：

```
## 🔒 Scope Lock
- 目标：[用一句话描述要做的事]
- 涉及文件：[列出预期会修改的文件，最多 10 个]
- 不涉及的文件：[明确列出看到了但不会碰的文件]
- 完成标准：[怎样算做完了？具体的、可验证的]
- 预计改动量：[行数级别估算：<50行 / 50-200行 / 200+行]
```

**如果你无法填写这个模板，说明任务定义不清晰——先问用户，不要猜。**

---

## 第二步：逐文件检查门（每次修改前）

在 edit/write 每一个文件之前，回答这三个问题：

1. **这个文件在 Scope Lock 的"涉及文件"列表里吗？**
   - 是 → 继续
   - 否 → **停下。** 这可能是范围蔓延。走第三步。

2. **这个修改直接服务于"目标"吗？**
   - 是 → 继续
   - 否 → **停下。** 不管它多小、多顺手、多合理。

3. **删掉这个修改，目标还能达成吗？**
   - 不能 → 这是必要修改，继续
   - 能 → **停下。** 这不是必要修改。

---

## 第三步：范围蔓延处理流程

当你发现自己想修改 Scope Lock 之外的东西时：

### 3.1 分类

| 情况 | 处理 |
|------|------|
| 不改会导致当前目标失败（编译错误、运行时崩溃） | 在 Scope Lock 中追加，注明原因，继续 |
| 不改不影响当前目标，但"看着不舒服" | **不改。** 记录到注释中，完成后告知用户 |
| 不改不影响当前目标，但"以后会有问题" | **不改。** 完成后作为建议告知用户 |
| 用户没要求但你觉得"应该一起做" | **不改。** 绝对不改。 |

### 3.2 记录但不执行

发现了想改但不应该改的东西？用这个格式记录：

```
📝 范围外发现：
- 文件：[path]
- 问题：[描述]
- 为什么不现在改：不在本次 Scope Lock 范围内
```

任务完成后，一次性报告给用户。

---

## 第四步：完成检查

任务完成时，对照 Scope Lock 逐项验证：

```
## ✅ Scope Check
- [ ] 所有"涉及文件"都已处理
- [ ] 没有修改"不涉及的文件"
- [ ] "完成标准"已满足
- [ ] 实际改动量与预估偏差 < 2x
- [ ] 没有引入新依赖（除非 Scope Lock 明确要求）
- [ ] 没有重命名/重构任何既有代码（除非 Scope Lock 明确要求）
```

**如果实际改动量超过预估 2 倍，在继续之前必须暂停并向用户确认。**

---

## 硬规则（违反任何一条 = 失败）

1. **永远不要在 bugfix 中做无关重构。** 修 bug 就是修 bug；当前 bug 的 canonical path 若必须跨文件替换或删除，调用方/被调用方的同步调整属于必要范围。
2. **永远不要"顺手"更新依赖版本。** 除非这正是任务目标。
3. **永远不要因为"风格不一致"而修改既有代码。** 除非用户明确要求统一风格。
4. **永远不要在改 A 文件时"顺便"改 B 文件。** 但若 B 是 A 的 canonical 调用方/被调用方，且不改会留下重复路径、编译错误或行为不一致，应把 B 追加到 Scope Lock 并注明原因。
5. **永远不要把"我觉得应该改"当作"用户要求我改"。** 这两个东西完全不同。

---

## 反模式识别

你正在范围蔓延的信号：

- "既然我已经在这个文件里了，不如也把……"  ← **停**
- "这个变量名不太好，我顺便重命名一下" ← **停**
- "这个 import 没有按字母排序" ← **停**
- "这个函数可以用更优雅的方式写" ← **停**
- "这个 TODO 注释提醒我应该处理一下" ← **停**
- "测试覆盖率不够，我多加几个" ← **停**（除非任务就是写测试）

**每一个"顺便"都是一次范围蔓延。没有例外。**
