# Failure Circuit Breaker — 失败熔断协议

你有一个致命倾向：修复失败后，用几乎相同的方式再试一次，期待不同的结果。这叫做**递归重试**，本 skill 的目的是在它发生前熔断。

---

## 核心机制：三次熔断

```
尝试 1: 失败 → 分析原因 → 换方式重试
尝试 2: 失败 → 分析原因 → 换方式重试
尝试 3: 失败 → 🔴 熔断。停止一切修复尝试。
```

**三次失败后不允许第四次尝试。没有例外。**

---

## 什么算"一次尝试"？

一次尝试 = 你修改了代码并验证了结果（编译/运行/测试）。

| 算一次尝试 | 不算一次尝试 |
|-----------|------------|
| 改了代码，编译失败 | 只是读了代码还没改 |
| 改了代码，测试失败 | 改了代码，还没验证 |
| 改了代码，lint 报新错误 | 修复了编译错误（这算"尝试成功"） |
| 改了代码，运行时报新错误 | 只是移动代码位置没有逻辑变更 |

## 每次失败后的强制流程

### 失败后第 1 步：记录失败

```
## ❌ Attempt N Failed
- 做了什么：[具体改动]
- 期望结果：[预期的正确行为]
- 实际结果：[实际的错误信息/行为]
- 错误本质：[根因分析，不是表面症状]
```

### 失败后第 2 步：差异分析

**在下一次尝试前，你必须回答：**

> "下一次尝试和上一次有什么**本质区别**？"

- 如果你的回答是"我改了不同的行" → **这不是本质区别。** 你可能只是在移动同一个问题。
- 如果你的回答是"我换了完全不同的策略" → 说出新策略是什么。
- 如果你说不出本质区别 → **不允许重试。** 直接进入熔断流程。

### 本质区别的定义

| 本质区别 ✅ | 不是本质区别 ❌ |
|-----------|--------------|
| 用不同的算法/数据结构 | 改了同一个算法的参数 |
| 调用不同的 API | 调用同一个 API 但换了参数 |
| 在完全不同的位置修复 | 在同一个函数的不同行修复 |
| 换了完全不同的依赖/库 | 换了同一个库的版本 |
| 重新理解了问题（有新证据） | "我觉得问题可能在别的地方" |

---

## 熔断后的流程

当三次尝试全部失败后，执行以下步骤：

### 步骤 1：恢复本次尝试

```bash
# 只撤销本次 Agent 自己记录的失败改动；不要覆盖用户或其他 Agent 的 dirty tree
# 优先使用补丁反向应用、编辑器历史或明确的单文件恢复方式
```

**禁止对未逐项确认的文件执行 `git checkout --`、reset、stash 或清理操作。** 如果无法安全恢复，停止并报告冲突，不得用破坏性命令“清场”。

### 步骤 2：写失败报告

```
## 🔴 Circuit Breaker Triggered
### 三次尝试摘要：
1. 尝试 1：[做了什么] → [失败原因]
2. 尝试 2：[做了什么] → [失败原因]
3. 尝试 3：[做了什么] → [失败原因]

### 根因分析：
[为什么三次都失败了？共同的阻塞因素是什么？]

### 我缺少什么：
[明确列出你不知道的、无法确认的信息]

### 建议的下一步：
- [ ] 选项 A：[具体描述]
- [ ] 选项 B：[具体描述]
- [ ] 需要用户提供的信息：[具体问题]
```

### 步骤 3：请求帮助

根据情况选择：

| 如果... | 那么... |
|---------|--------|
| 你不理解错误的根因 | 咨询 Oracle，带上完整的失败报告 |
| 你理解根因但所有方案都试过了 | 问用户，给出你的分析和选项 |
| 错误可能来自外部（库 bug、环境问题） | 告诉用户你怀疑是外部问题，给出证据 |

## 特殊场景：链式错误

链式错误 = 改了 A 导致 B 报错，改了 B 导致 C 报错，改了 C 导致 A 报错。

**这是最危险的递归重试模式。** 识别方法：

```
如果你改的文件 F 在之前的尝试中已经改过一次 → 你可能在循环
如果你修的错误 E 和之前某次遇到的错误一模一样 → 你肯定在循环
如果你回到了第一次尝试时改动的那个文件 → 🔴 立刻熔断，不等三次
```

**链式错误触发立即熔断。不需要等三次。**

---

## 编译错误的特殊规则

编译错误（TypeScript 类型错误、import 错误等）有自己的计数方式：

```
同一个编译错误（同一个文件、同一个错误代码）连续出现 3 次 → 熔断
不同的编译错误交替出现 2 轮 → 链式错误，立即熔断
```

### 禁止的编译错误"修复"方式

永远不允许使用以下方式"修复"编译错误：

| 禁止 | 为什么 |
|------|--------|
| `as any` | 只是隐藏了类型错误 |
| `@ts-ignore` / `@ts-expect-error` | 同上 |
| `// eslint-disable` | 不解决问题 |
| 删除报错的测试 | 测试没错，你的代码错了 |
| 把严格检查改成宽松检查 | 方向搞反了 |

## 反模式识别

你正在递归重试的信号：

- "让我试试另一种方式" 但你说不出和上次有什么**本质区别** ← **熔断**
- 你在同一个文件的 edit 调用次数 > 3 ← **高度警惕**
- 你的"修复"引入了新的、不同的错误 ← **链式错误风险**
- 你在读同一个错误信息第三次 ← **你在循环**
- 你的修复越来越大（从改 1 行到改 10 行到改 50 行）← **你在挖坑**
