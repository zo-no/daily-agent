# Agent 计划、记录与 Google Calendar 三能力拆解

日期：2026-09-05
状态：拆解完成；LN-084～LN-086 均已有本地候选实现与自动化回归，但仍待真实账号、OAuth、生产部署和独立验收
对应看板：LN-084、LN-085、LN-086；对应规格包：`specs/REQ-20260905-01-agent-mcp-bridge/`、`specs/REQ-20260905-02-agent-plan-record-authoring/`、`specs/REQ-20260905-03-google-calendar-realtime/`

## 结论先行

这次应采用“MCP 负责可调用的数据与动作，Skill 负责语义、工作流和安全提示”的组合，而不是只做一个 Skill。Skill 能告诉 Codex 或 Claude 如何理解“计划”和“记录”，但不能可靠地读取当前账号数据或执行账号隔离的写入；MCP 才是连接实时数据、受控读取和受控动作的接口。

三项能力必须共用一套版本化领域契约，并保留现有的账号隔离、本地优先、revision/CAS、备份兼容和显式确认边界：

1. Agent 读写计划：按时间块读取和提出/确认新增、修改、删除计划。
2. Agent 读写记录：读取指定日期/时间范围的记录，提出/确认新增、修改、删除记录，并允许指定已有领域与分类。
3. Google Calendar 近实时同步：本地计划与 Log Note 管理的 Google 事件双向同步；Google 原有事件仍只读，不自动变成 Log Note 计划。

## 一、先把“计划”和“记录”定义清楚

### 1. 计划（Plan）

计划是“未来准备做什么”的时间安排，主维度是时间块。当前规范实现是 `planBlocks`，核心字段为：

- `id`：Log Note 内部稳定 ID。
- `date`、`startTime`、`endTime`：计划所在日期和起止时间；结束时间必须晚于开始时间。
- `title`：计划标题，不等同于记录正文。
- `source`：`local` 或 `google`。`local` 可编辑，`google` 是外部日历只读事件。
- `flexibility`：`fixed`、`movable` 或 `resizable`。
- `externalRef`：仅用于受管 Google 事件的关联，不把 Google token 或完整事件对象写入主文档。

计划表达意图，不证明事情已经发生；计划不会因为 Agent 复盘或日历同步而自动变成记录，也不会被记录内容静默改写。Agent 修改计划时必须先返回时间、标题和来源指纹的提案，再由调用方明确确认。

### 2. 记录（Record）

记录是“已经发生或正在发生的事实”，主维度是日期、发生时间、正文和分类。当前规范实现是 `entries`，核心字段为：

- `id`、`date`、`time`：记录身份、自然日和时间点；旧数据继续兼容 `HH:mm`。
- `content`：作者正文，原文是事实来源，任何 Agent 都不能静默重写。
- `categoryId`：恰好一个已有分类；分类属于既有“领域 → 分类”结构。
- `templateId`、`fieldValues`、`tags`、`attachments`：结构化记录和本地附件的既有扩展字段。

用户提出的“什么时间段干了什么”需要在后续产品决策中明确：是继续使用一个发生时间点，还是为记录增加可选 `endTime`/区间语义。第一阶段沿用现有 `entries.date/time` 时间点语义，Agent API 不接受 `endTime` 或区间字段；只有单独的 schema、编辑器、备份兼容规格通过后，才允许另立任务落地区间字段。无论最终选择哪一种，记录仍然是事实，不能由计划或 Google 事件自动生成并写入。

### 3. 两者的边界

| 维度 | 计划 | 记录 |
| --- | --- | --- |
| 语义 | 未来意图/安排 | 已发生事实/过程记录 |
| 时间 | 必须是起止时间块 | 当前是时间点；区间语义待单独决策 |
| 正文 | 标题短文本 | 作者正文，可包含较长叙述和 Markdown |
| 分类 | 不要求分类 | 使用一个已有分类，不自动建分类 |
| Google | Log Note 管理的本地计划可同步为受管事件 | 不从 Google 事件自动生成 |
| Agent 写入 | 提案 → 确认 → 原子提交 | 提案 → 确认 → 原子提交；原文不得静默改写 |
| 离线 | 本地计划可继续编辑 | 本地记录可继续新增、浏览、搜索、编辑、删除 |

## 二、外部 Agent 的接口形态

### MCP 是动作和数据面

建议提供一个账号绑定的 Log Note MCP server，至少暴露以下只读资源和动作：

- 资源：按日期或范围读取 `plans`、`records`、`categories`，返回脱敏后的稳定字段和 `revision`/`fingerprint`。
- 读动作：`list_plans`、`list_records`、`get_plan`、`get_record`，所有查询都要求日期/范围上限。
- 写动作：`propose_plan_change`、`propose_record_change`，只返回版本化提案，不写数据。
- 提交动作：`commit_change`，必须携带提案 ID、显式确认、目标 ID、原始 fingerprint 和 expected revision；服务端重新读取并校验后只执行一次原子提交，再读回结果。

MCP 不能暴露 Supabase service key、Google token、浏览器 localStorage、完整账号文档、图片 Blob 或 `commitData` 的任意执行权。接口应拒绝未知字段、越界 ID、重复操作、过期提案、跨账号目标和 stale revision。

### Skill 是语义和工作流面

随 MCP 提供一个轻量 Skill，内容只包含以下语义与流程；其 Codex 项目级主路径为
`.agents/skills/log-note-agent/SKILL.md`：

- 计划/记录的定义和区别；
- 何时先读、何时先提案、何时必须请求确认；
- 记录分类只能从已有结构中选择；
- 不把“计划完成”写成“记录已发生”；
- 不在没有读回证据时声称已保存；
- 对用户说清楚修改范围、日期、时间、分类和可能的冲突。

Skill 不承担鉴权、数据读取、持久化或绕过 MCP 的隐藏写入。

### 需要先解决的桥接问题

当前 Log Note 的浏览器缓存由已登录浏览器拥有，`commitData` 是本地先写和云同步入口。工作树目前已有候选的 MCP schema、stdio/loopback queue、路由、浏览器配对泵、设置页确认 UI、Skill 和 `commitData` 控制器接线，但真实 Codex/Claude 发现、真实账号和完整安全回归仍未验证。实现会话必须先在以下两种方案中选定一种，并记录 ADR：

1. **本地配对桥接（推荐优先评估）**：Codex/Claude 启动本地 MCP 进程，通过一次性配对把动作转发给当前登录的 Log Note，再由浏览器 `commitData` 提交；优点是保留本地优先，缺点是需要浏览器与进程的配对和唤醒协议。
2. **账号级远程 CAS 适配器**：MCP 使用用户 OAuth 访问同一账号云文档，沿用严格 schema、revision/CAS 和读回；浏览器通过 revision 变化重新合并。优点是 Claude/Codex 无需依赖打开的浏览器，缺点是必须补足外部写入后的本地缓存更新、撤销和离线一致性说明。

无论选哪种，MCP 都不能直接写 Supabase 表或另建一套记录/计划存储。

## 三、Google Calendar 近实时同步边界

“实时”在工程上应定义为：Google 事件变化在可接受延迟内进入当前账号的本地缓存，本地计划变化在可接受延迟内反映到 Log Note 管理的 Google 事件；不承诺毫秒级一致。

建议分两层实现：

1. **同步契约**：延续现有 `externalRef`、`logNoteManaged` 和 `logNotePlanId` 标记；本地计划只创建/更新/删除自己管理的 Google 事件，Google 原有事件只读展示。
2. **变化通知**：评估 Google Calendar push channel + webhook；若部署环境不允许稳定 webhook，则退回有界轮询，并在界面明确“上次同步时间”和延迟状态。每次变化都要以事件 ID、etag 或 sync token 去重，账号切换、撤销授权和过期 channel 必须使旧回调失效。

冲突规则必须固定：

- Log Note 管理事件被 Google 用户修改：以 etag/CAS 检测冲突，不静默覆盖；进入待处理状态，由用户明确选择“保留本地并重新创建”“采用 Google”或“手工处理”。
- Google 原有事件与本地计划重叠：只展示事实，不自动合并或改写计划。
- 本地删除计划：只删除对应的受管 Google 事件。
- Google 删除受管事件：保留本地计划并标记同步缺口，由用户明确选择重新创建事件、采用远端删除事实或手工处理。

## 四、按三个能力组织可选的工作会话

三个能力分别是 Agent 计划、Agent 记录和 Google Calendar 同步。MCP/Skill
桥接不是第四个产品能力，而是前两个 Agent 能力共用的技术接口；它仍保留独立看板项
`LN-084` 和独立验收门槛，避免把“能发现 MCP”误当成“业务写入已完成”。

创建三个 Codex 线程只是便于架构分工和单写者协作，不是产品能力、MCP 注册或日常使用的前置条件。
只要 MCP server 已注册、Log Note 浏览器已配对，任何支持 MCP 的 Codex 或 Claude 会话都可以
调用这些资源和动作。若多个会话同时修改同一工作树，仍必须由总控协调为一次一个 writer。

### 会话 1：Agent 计划能力（LN-084 前置 + LN-085 计划子切片）

`date + startTime + endTime + title + flexibility` 的时间块语义处理，Google-origin 计划只读。

### 会话 2：Agent 记录能力（LN-085 记录子切片）

### 会话 3：Google Calendar 近实时同步（LN-086）

目标：在现有 LN-067 同步基础上补齐变化通知、增量拉取、channel 续期、etag 冲突和 UI 状态。
依赖：会话 0 的冲突政策；不依赖 MCP 才能单独验收。
验收：本地计划→Google、受管 Google→本地、Google 原有事件只读、重复/乱序/过期回调、撤销授权、离线恢复、账号切换和真实 Google 账号人工证据。

## 五、共同不可违反的约束

- AI/Agent 返回永远是未受信任提案，不是写入指令。
- 所有写入必须绑定当前账号、目标、请求 ID、fingerprint 和 expected revision。
- 确认前不得改记录、计划、Supabase、备份或 Google；失败、取消、过期、离线和冲突均零写入。
- 不新增第二套记录/计划存储，不把 MCP server 当成新的产品数据库。
- 不向 Agent 暴露 token、service key、完整账号文档、图片 Blob、Google 私有字段或其他账号数据。
- `npm run check` 是代码任务的必要门禁；交互改动还要通过 `npm run design:check` 和移动端回归。
- 每个会话只允许一个 writer；返回 `Returned` 后由总控独立验收，不能把聚焦测试当成 `Accepted`。

## 七、三次只读审查后的总控建议

三个独立设计会话已对当前工作树完成只读核对，结论如下：

| 能力 | 当前真实状态 | 首选实现顺序 |
| --- | --- | --- |
| MCP/Skill | 已有严格的今日工作总结 Tool 和多个 AI proposal；工作树已有候选 MCP SDK、schema、stdio/loopback queue、浏览器配对/提案 UI 和 Skill，但尚无真实客户端证据 | 先做本地配对桥接，让浏览器继续拥有本地状态和 `commitData`；远程 CAS 作为后续适配器 |
| Agent 计划/记录 | `planBlocks` 和 `entries` 已分别有规范化、编辑器、分类 allowlist、revision/CAS 和备份链路 | 先复用现有字段完成读/提案/确认/读回；记录 `endTime` 暂不落库 |
| Google Calendar | 已支持浏览器 token、受管事件幂等创建/更新/删除、缓存和 900ms 计划变更同步 | 先补 `syncToken` 增量轮询、删除 tombstone、etag 冲突和可观测状态；目标部署具备 refresh token、队列和公网 HTTPS 后再启用 push channel/webhook |

审查得到的关键证据：

- `src/lib/plan-model.mjs` 是计划块的规范入口，要求合法日期、起止时间和唯一 ID；`source=google` 的计划必须只读。
- `src/lib/data.mjs` 的 `normalizeState()` 是记录、结构和备份的规范入口，当前记录只有 `date/time/content/categoryId` 等字段，没有 `endTime`。
- `src/app/log-note-data-provider.js` 的 `commitData` 先写当前账号 localStorage，再经 revision/CAS 同步；不能从 MCP 另建一条直接写库路径。
- `src/modules/agent-bridge/daily-log/` 已证明“严格 schema + source fingerprint + `preview-required`”模式可复用，但 Mastra Tool 注册不等于 MCP 暴露。
- `src/app/google-calendar-provider.js` 当前使用内存 token、受管事件 reconciliation 和全量窗口读取；没有 `syncToken`、`events.watch`、Webhook 或后台 worker。

因此，会话 0 的默认建议是：

1. **桥接**：选择本地配对；允许一个已登录的 Log Note 浏览器标签页作为数据拥有者，MCP 进程只做受控转发，不持有 service key。
2. **记录时间**：第一阶段沿用现有时间点 `time`，不把“时间段”偷偷扩展到备份和编辑器；若真实使用证明区间必要，再单独立项增加可选 `endTime`。
3. **实时定义**：首版定义为“页面可见期间的增量同步 + 网络恢复立即同步”；服务端 push 作为部署条件满足后的增强，不在缺少安全 refresh token/worker 时虚假承诺后台实时。

当前三点已形成默认架构基线：会话 1 负责先验收 LN-084 再交付计划子切片；会话 2
只能在 LN-084 Accepted 后交付记录子切片；会话 3 可独立进入 LN-086 的 syncToken/轮询
方案审查，但不得把未获部署批准的 push 当成已实现能力。LN-085 的最终 Accepted 由总控
在线程 0 汇总计划与记录两部分证据后决定。
