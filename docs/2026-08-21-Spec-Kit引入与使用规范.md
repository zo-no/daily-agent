# Spec Kit 引入与使用规范

- 引入版本：Spec Kit `0.16.5`
- Codex 集成：`.agents/skills/speckit-*`
- 项目配置：`.specify/`
- 引入日期：2026-08-21

## 目的

从本次起，Log Note 的新功能和有实质行为变化的改动统一使用 Spec Kit 的规格驱动流程，
减少需求、方案、任务和验收之间的遗漏。它是现有项目治理的执行层，不替换已有事实源。

## 事实源分工

| 决策 | 唯一事实源 |
| --- | --- |
| 操作规则、产品红线、单写多读 | `AGENTS.md` |
| 长期产品行为、准入评分、退出条件 | `product.md` |
| 优先级、依赖、任务状态、验收证据 | `PROJECT_BOARD.md` |
| 单个功能的用户故事、方案、接口、任务 | `specs/<feature>/` |
| Spec Kit 治理原则 | `.specify/memory/constitution.md` |

Spec 包可以引用上层事实源，但不能创建第二个 backlog、改变板项状态或自行宣布 Accepted。

## 标准流程

1. 在 `PROJECT_BOARD.md` 找到一个已有的 `LN-###` 项目；没有 Ready、依赖或权限时先解决看板状态。
2. 使用 `$speckit-specify` 创建一个功能包，并在 `Board Item` 写明板项编号。
3. 对产品范围、隐私、离线、账号、迁移或外部授权存在实质歧义时，先用
   `$speckit-clarify`。
4. 使用 `$speckit-plan`，明确现有代码复用、数据流、信任边界、写范围、测试和回滚。
5. 需要额外需求质量评审时使用 `$speckit-checklist`，随后用 `$speckit-tasks` 生成任务。
6. 使用 `$speckit-analyze` 检查 spec、plan、tasks 和 Constitution 的覆盖与矛盾。
7. 经总控确认 Ready、单写槽空闲且权限明确后，按 tasks 执行；实现者只返回证据。
8. 总控独立核对 diff、测试、构建、截图/手工会话和看板验收标准，再更新
   `PROJECT_BOARD.md`。

## 必须保留的门禁

- 普通快速记录不得增加必填决策或额外步骤。
- 已认证设备必须能离线记录；账号缓存和图片命名空间必须隔离。
- 原始记录不得被 AI、导入、迁移或派生能力静默改写。
- JSON、Markdown 和便携附件备份必须保持兼容。
- 新网络/AI 能力必须写清发送字段、授权、密钥、限流、超时、日志、降级和移除方式。
- 相关回归、`npm run design:check`（交互改动）和完整 `npm run check` 必须通过。
- 不得未经明确授权提交、推送、发布、部署、删除、重置、改写历史、修改 OKR 或合并 worktree。

## 升级规则

运行 `specify self check` 检查版本；升级前先审阅 CLI 变更和工作树。官方管理文件可由 CLI
刷新，项目定制只放在 Constitution 和 `.specify/templates/overrides/`，避免升级覆盖项目规则。
升级后至少验证：Skill 文件、模板解析、现有 `AGENTS.md`、`npm run design:check`、
`npm test`、`git diff --check`。
