# LN-053｜Google 日历只读对齐接入方案

## 决策摘要

第一版只接入 Google Calendar 的只读事件，采用用户主动连接、主动刷新的方式，把日历事件显示在现有“月历 → 日计划”中，并与同一天、同一时间附近的 Log Note 记录共同浏览。

- Google Calendar 提供“计划发生什么”。
- Log Note 记录保留“实际发生什么”。
- 不自动改写、创建、分类或删除原始记录。
- 不从 Log Note 写回、移动或删除 Google 事件。
- 不把 Google 账号、网络或授权变成快速记录的前置条件。

双向同步、后台自动同步、提醒和 Agent 自动改日程不属于本项；这些能力需要服务器端令牌、冲突策略和新的隐私审批。

## 功能准入

1. **核心循环贡献**：改善按天浏览和回看，让用户在日计划中比较“计划时间块”和带时间的实际记录；不改变快速记录步骤。
2. **用户证据**：产品所有者提供 Google Calendar 单日视图截图，并明确要求把 Google 日历加入项目、与每天的记录对齐。
3. **默认界面成本**：连接入口只放在设置页；首页不新增常驻按钮。未连接时，现有本地月历和日计划保持原样。
4. **离线、隐私、可逆与备份**：只申请 `calendar.readonly`；授权由用户显式触发；访问令牌不写入 Log Note 备份；断开连接后可清除本地 Google 事件缓存，不影响 `entries` 和本地 `planBlocks`。
5. **测试与隔离**：Google API 映射和增量替换使用纯函数单测；浏览器 E2E 使用假事件，不依赖真实账号；真实账号只做独立手工验收。接入层和 Google 来源事件可整体移除。
6. **失败/不采用条件**：14 天内很少查看对齐结果、连接明显降低记录频率、用户误以为已经双向同步、重复/漏事件不可解释，或 OAuth/缓存导致核心离线门禁退化时，保持隔离或移除。

准入判断：以只读、手动刷新、设置页次级入口实施时可作为隔离试点；双向或后台同步不进入当前 MVP。

## 第一版用户流程

1. 在“设置 → Google 日历”点击“连接”。
2. Google 授权页只请求查看日历事件。
3. 默认选择主日历；第一版不要求用户先做多日历配置。
4. 用户点击“刷新”，拉取选中日期前后 14 天的事件并缓存在本机。
5. 打开“月历 → 日计划”：
   - Google 事件显示来源标识并保持只读；
   - 本地计划仍可新增、编辑和删除；
   - 当天记录按其时间显示为轻量实际记录标记，点击进入既有记录查看/编辑路径；
   - 不自动判断某条记录必然属于某个会议或事件。
6. 在设置页可以断开连接，并选择是否同时清除本地 Google 事件缓存。

## 数据边界

现有 `planBlocks` 已预留：

```text
source: "local" | "google"
externalRef: {
  provider: "google",
  calendarId,
  eventId,
  etag
}
```

接入时遵守以下规则：

- `source: "local"` 的计划块仍由 Log Note 管理。
- `source: "google"` 的事件由 Google 端权威管理，在 Log Note 中只读。
- Google 刷新只替换成功拉取时间范围内的 Google 来源事件；请求失败时不得删除旧缓存。
- 本地记录 `entries` 不增加 Google 必填字段，也不因同步被改写。
- Google 访问令牌只保存在页面运行内存中；刷新页面后可重新授权。第一版不在浏览器长期保存令牌。
- Google 事件标题、时间和来源引用属于用户数据；若进入完整 JSON/便携备份，恢复后只能作为离线缓存展示，不能代表仍与账号保持连接。
- OAuth Client ID 可以公开出现在前端配置中；OAuth Client Secret 不得进入浏览器代码、仓库或 `NEXT_PUBLIC_*` 环境变量。

## Google Cloud 设置

1. 创建或选择一个 Google Cloud Project。
2. 启用 **Google Calendar API**。
3. 配置 OAuth consent screen：
   - 应用名称使用 `Log Note`；
   - 添加本人作为测试用户；
   - 只申请 `https://www.googleapis.com/auth/calendar.readonly`；
   - 不申请写入、删除或完整账号权限。
4. 创建 **OAuth 2.0 Client ID → Web application**。
5. 添加 Authorized JavaScript origins：
   - 本地开发：`http://localhost:3100`
   - 正式环境：未来实际部署的 HTTPS Origin，例如 `https://log-note.example.com`
6. 将 Client ID 配置为：

```text
NEXT_PUBLIC_GOOGLE_CALENDAR_CLIENT_ID=xxxx.apps.googleusercontent.com
```

7. 不提交 `.env.local`，不在仓库中保存 Client Secret。

## 技术实现顺序

### A. 连接边界

- 在设置页新增独立 Google 日历区块。
- 仅在用户点击连接后加载 Google Identity Services。
- 使用浏览器 Token Client 请求 `calendar.readonly` access token。
- 连接状态、最近刷新时间和错误信息必须可见；不得用静默失败冒充已同步。

### B. 事件读取与映射

- 调用 Calendar List，第一版默认使用 `primary`。
- 调用 Events List：`singleEvents=true`、`orderBy=startTime`，时间范围为选中日期前后 14 天。
- 分页读取完整结果；保存 `event.id`、`etag`、calendar ID、标题和本地时区下的开始/结束时间。
- 重复事件按具体实例处理，不能只按系列 ID 去重。
- 全天事件需要在日计划顶部新增独立“全天”区域；在该区域完成前不得把全天事件伪装成 `00:00` 时间块。
- 已取消事件和刷新后消失的事件，只在成功完成对应时间范围的完整读取后移除本地缓存。

### C. 与每天记录对齐

- 同一日视图同时呈现 Google 计划时间块、本地计划时间块和 Log Note 实际记录时间标记。
- “对齐”第一版只做时间上的并置，不做自动语义归因。
- 后续若需要把记录显式关联到事件，应由用户主动选择，并以可删除的派生引用保存；仍不得修改记录正文。

## 验收标准

- 未配置 Client ID 时，应用可正常构建和使用，只在设置页说明尚未配置。
- 未连接、拒绝授权、令牌过期、API 限流、离线和 Google 服务失败均不影响核心记录流程。
- 只请求 `calendar.readonly`，浏览器和仓库中不存在 Client Secret。
- 手动刷新可幂等更新主日历事件；重复刷新不产生重复块。
- 跨时区、夏令时、重复事件、全天事件、取消事件和分页均有测试或明确手工证据。
- Google 来源事件只读，本地计划仍可独立编辑。
- 当天记录可从日计划进入既有详情，但不会被自动改写或自动绑定事件。
- 断开连接可清除授权状态和 Google 缓存，不删除原始记录或本地计划。
- `npm run check`、移动端 320/390/1280 复核和离线 PWA 回归通过。

## 启动实现所需输入

- Google OAuth Web Client ID。
- 本地开发 Origin 是否固定为 `http://localhost:3100`。
- 未来正式部署的 HTTPS Origin；若尚未确定，可先只配置 localhost，真实部署验收后补充。
