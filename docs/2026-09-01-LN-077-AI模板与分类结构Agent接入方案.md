# LN-077｜AI 模板与分类结构 Agent 接入方案

## 结论

建议把这次能力定义为一个 **AI 结构助手**，包含三个受限模式：

1. 首次创建：无输入直接使用本地默认结构，零模型请求；有输入一次生成一个完整模板。
2. 已有模板优化：只对当前模板做可解释的小改，不重建结构。
3. Agent 整理：优先使用已有分类；确有结构缺口时，最多提出一个“领域 + 分类 + 模板”结构包。

技术上首选 **Dify Workflow**，不首选自由 Agent。Dify 只负责“受限输入 → 结构化 proposal”，没有 Log Note 数据库、本地缓存或写工具；Log Note 继续负责账号鉴权、隐私裁剪、schema 校验、差异预览、用户确认、本地先写和 revision 冲突。这样既使用成熟平台，又不把核心数据安全交给平台。

首期先做 Dify Cloud + 合成数据 PoC。真实笔记在 `LN-007/LN-009` 与平台数据政策评审完成前保持关闭；若真实数据必须留在自控基础设施，再单独评估 Dify 自部署。

## 需求理解

| 场景 | 用户问题 | 目标结果 | 明确不做 |
| --- | --- | --- | --- |
| 首次创建 | 不知道一个好模板应有哪些字段 | 一次得到一个完整、可预览模板 | 不一次生成整套领域树；不强制首次登录问卷 |
| 无输入 | 用户没有给任何偏好 | 直接沿用本地默认结构，0 Token | 不远程“重新生成默认模板”；不创建重复随手记 |
| 已有模板 | 长期使用后只想更顺手 | 对所选模板返回一个保守 patch | 不移动模板、不改类型/周期、不删除或重排字段 |
| Agent 整理 | 新内容找不到合理归属 | 先匹配已有分类；必要时提一个完整新结构包 | 不自动建结构、不自动搬记录、不改原文 |

这里的“首次”建议定义为 **当前账号首次主动进入模板助手的创建场景**，而不是每次登录或每台设备。普通快速记录仍然直接进入记录，不增加 AI 决策。

## 当前系统事实

- 当前新状态已经本地内置 4 个领域、6 个分类和 11 个模板，其中包含“随手记”；因此无输入路径本来就可以完全不联网。
- 当前结构管理已经能手动新建领域、分类和模板，提供自由文本、结构化、每日单值三个预设，并通过 `commitData` 本地先写。
- 当前 Diary Agent 和智能整理被产品规则限定为已有分类，不允许创建领域/分类/模板；新结构模式是一个需要单独批准的边界扩展。
- 当前 entry 保留 `templateId`，可以在本机计算模板使用次数、活跃天数和最近使用日期，不需要发送历史正文。
- 现有服务端 AI 路由已经具备同源、Bearer、Supabase 用户校验、限流、超时、Zod 和取消模式，可以复用安全骨架。

## 产品方案

### 模式 A：首次创建完整模板

入口位于 Settings → Record setup 的新建模板流程，不出现在首页，也不弹首次登录模态。

```text
用户进入模板助手
  ├─ 没有需求文本 → 沿用本地默认结构 → 结束（0 请求）
  └─ 有需求文本 → 生成一个完整模板 proposal → 预览 → 确认/拒绝
```

一个“完整模板”至少自洽地包含：

- 模板名称；
- 线性/周期记录；
- 自由文本/结构化/单值输入；
- 提示语和最多 3 个标签；
- 周期配置（如果适用）；
- 最多 6 个字段，每个 select 最多 6 个选项。

一次只生成一个模板。模型不生成持久 ID 和排序；确认后由 Log Note 本地生成。

### 模式 B：已有模板保守优化

入口只出现在当前模板的编辑面板。首期所谓“过去的记忆”不是把历史日记全部发给模型，而是：

- 当前模板本身已经沉淀的字段、提示语和设置；
- 本机派生的使用次数、活跃天数和最近使用日期；
- 用户本次明确提出的调整要求。

允许变更：

- 名称、提示语、标签；
- 字段名称、占位语、必填状态；
- 最多新增一个字段。

禁止变更：

- 所属分类、记录类型、输入模式、周期配置；
- 删除、重排、更换已有字段 ID；
- 改变已有字段类型和选项语义；
- 修改任何历史记录。

如果模型的一个响应同时包含合法和越界修改，整份拒绝，不静默套用“看起来安全”的部分。证据不足时可以返回“无需调整”。

### 模式 C：Agent 新结构提案

此模式是现有 Diary Agent 的后续阶段，不改变默认行为：

1. 用户主动唤醒 Agent 并让它整理所选记录。
2. Agent 必须先尝试一个已有分类。
3. 只有现有结构确实不能承载时，返回一个结构包：
   - 一个领域草案；
   - 领域下一个分类草案；
   - 分类下一个完整模板草案；
   - 简短缺口理由和来源记录 ID。
4. 用户进入完整预览并确认后，三层对象一次本地创建。
5. 原记录的正文、分类和模板归属全部保持不变；是否调整记录由用户以后单独决定。

这样把“发现结构缺口”和“重分类历史记录”拆开，避免一次确认产生两类不可预期变化。

## 为什么选 Dify Workflow，而不是自由 Agent

Dify 官方工作流已经提供输入、条件分支、参数抽取、结构化输出、模板节点、测试和发布；确定性格式还可以用模板节点完成，不消耗模型 Token。[Dify Workflow quick start](https://docs.dify.ai/en/guides/application-orchestrate/creating-an-application)

| 方案 | 优点 | 本项目代价 | 判断 |
| --- | --- | --- | --- |
| Dify Workflow | 低代码编排、Prompt/模型可视化、结构化输出、运行记录、Cloud/自部署 | 仍需一个窄 adapter；Cloud 增加数据处理方 | 首期推荐 |
| LangGraph | durable execution、HITL、checkpoint、memory | 仍要自己写图、状态、部署和存储 | 当前过重，长时 Agent 再选 |
| OpenAI Agents SDK | agent loop、sessions、guardrails、tracing、审批 | code-first，应用仍负责部署、工具、状态和产品 UI | 多工具 Agent 再选 |
| 现有 AI SDK 直连 | 仓库已有、依赖最少、单次结构化输出直接 | Prompt、分支、版本和观测仍由项目自行维护 | 可靠备选，不符合本次平台优先 |

LangGraph 官方定位是低层、长时、有状态 Agent runtime，重点是 durable execution、human-in-the-loop 和 persistence；当前一次 proposal 不需要外部 checkpoint。[LangGraph overview](https://docs.langchain.com/oss/python/langgraph/overview) [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence)

OpenAI 官方也把 Agents SDK 定义为 code-first，服务器仍拥有部署、工具实现、状态和审批；它更适合重复工具调用、多个 specialist 和可恢复审批，而不是当前一次结构化生成。[OpenAI Agents SDK](https://developers.openai.com/api/docs/guides/agents)

Dify 可使用 Cloud 或自部署，但官方 Docker Compose 本身包含多个持久服务和 worker，不能把自部署理解成“没有运维成本”。[Dify official repository](https://github.com/langgenius/dify) [Dify Docker deployment](https://github.com/langgenius/dify/blob/main/docker/README.md)

## 推荐架构

```text
Record setup / Diary Agent
          │
          │ 本地判断 mode、空输入、使用统计、结构摘要、内容裁剪
          ▼
POST /api/organize/template-proposal
          │
          │ Origin + Bearer + user verify + rate limit + 64 KiB + timeout
          ▼
WorkflowAdapter（server-only Dify key）
          │
          ├─ create    → template-create-v1
          ├─ refine    → template-refine-v1
          └─ structure → structure-propose-v1
          │
          ▼
Dify Workflow（无 Log Note 工具 / 无产品写权限）
          │
          ▼
strict schema / 业务规则二次校验
          │
          ▼
浏览器结构指纹检查 → 差异预览 → 用户显式确认
          │
          ▼
commitData → 当前账号本地先写 → revision-checked sync
```

建议拆成三个 Dify workflow，而不是一个巨大 workflow 或一个自由 Agent：三个模式的数据边界、风险和发布节奏不同，可以单独关闭、回滚和比较质量。

## 数据与权限边界

| 模式 | 可外发 | 默认不得外发 |
| --- | --- | --- |
| create | 用户需求、语言、结构名称摘要、用户选择的目标分类 ref | 任何记录正文、附件、图片、计划、账号信息 |
| refine | 一个模板、用户要求、useCount/activeDays/lastUsedAt | 历史正文、entry IDs、其他模板详情、附件/图片 |
| structure | 最多 12 条用户主动选择的普通记录，每条最多 1000 字；现有结构摘要、语言 | 未选记录、周期记录、计划、附件/图片、完整文档 |

所有模式都禁止：

- Supabase service role、访问令牌、账号 ID/email；
- localStorage/IndexedDB 访问；
- `commitData`、记录写入、结构写入、MCP 或 webhook 回写；
- 在 Dify 保存可跨账号使用的记忆。

浏览器 access token 只到 Log Note 同源服务端做用户验证，不转发给 Dify或模型。应用日志只记录 request ID、模式、耗时、字节和结果码，不记录正文或 proposal。

## Token 与成本控制

1. 空输入和本地默认在调用模型前结束。
2. 重名、明显重复结构和基础规则先本地判断。
3. 每次用户动作最多一次模型请求，不做自主工具循环或自动重试。
4. create/refine 默认不发送历史正文。
5. structure 只发送用户主动选择的最多 12 条、每条最多 1000 字。
6. 输出固定为一个 proposal：最多一个模板或一个三层结构包。
7. 固定 schema/说明作为稳定 Prompt 前缀，动态内容置后；提供方支持时利用 Prompt cache。
8. 记录 Dify 合成 PoC 的输入/输出 Token、延迟、错误和单次费用，用实测而不是估算决定是否继续。

## 失败、离线和并发

- 离线、无配置、限流、超时或非法响应只显示“暂不可用”；默认结构和手动模板编辑继续可用。
- Stop、离页、切账号、切模式、切目标会取消请求并废弃迟到响应。
- proposal 绑定生成时的结构 fingerprint；确认时结构已变化就标记过期，要求重新生成。
- fingerprint 只防本地 proposal 过期，不替代 Supabase CAS。云端 revision 冲突继续走现有冲突处理。
- localStorage 真正写入失败时不显示成功，不自动重试模型；预览保留供用户稍后重试保存。

## 分阶段实施

### Phase 0：平台 PoC，不接真实数据

- 用固定合成样本搭建和发布三个 Dify workflow。
- 验证 schema 有效率、越界拒绝、一次调用、Token、延迟、费用和日志边界。
- 目标：schema 有效率至少 95%，越界 patch 接受率 0%，每个动作最多一次调用，中位延迟不超过 8 秒。

### Phase 1：本地默认 + 完整模板创建

- 先实现零请求默认路径和 create proposal。
- 只接 Record setup，不改 Diary Agent。
- 证明预览前零写入、确认后一个普通 template、备份/恢复/离线兼容。

### Phase 2：已有模板保守优化

- 增加本地 usage summary 和 strict patch schema。
- 只修改一个目标模板的 allowlist；越界混合响应整份失败。
- 14 天观察确认率、复用和实际填写摩擦。

### Phase 3：Agent 新结构包

- 先更新并批准产品/设计真源，明确取代“Agent 不得创建结构”的现有规则。
- Agent 继续优先已有分类；新结构作为独立终态和完整预览。
- 确认只创建三层结构，不搬记录。
- 若多数建议能被已有分类覆盖，Phase 3 保持隔离或不进入主线。

## 验收与退出条件

进入下一阶段前必须同时满足：

- 空输入外部请求数为 0；远程动作最多一次请求、一个 proposal。
- 任何非法/越界响应不能部分应用，确认前记录和模板 payload 不变。
- 账号切换、迟到、stale、离线和失败均为 0 错误写入、0 跨账号显示。
- 320/390/426/768/1280px 的结构页和 Agent 预览满足 44px、键盘、焦点和无横向溢出。
- `npm run design:check`、聚焦测试、`npm run check` 和 `git diff --check` 通过。
- 14 天隔离观察中确认率至少 50%、非法提案不超过 20%、成功请求中位可感知延迟不超过 8 秒，并至少发生一次二次使用。

任一隐私、原文、账号、离线、备份或质量门禁回归直接停止。平台成本/运维超过模板价值，或者新结构提案多数没有真实缺口，也停止扩大。

## 决策项—待确认内容

1. **首次无输入的默认**：建议沿用当前完整本地默认结构，不再额外创建一个“默认模板”。若你希望新账号只保留一个“随手记”，那会涉及默认数据与迁移的另一项产品改动，应单独讨论。
2. **首次的定义**：建议按“账号首次主动进入模板助手”而不是“首次登录”；避免干扰快速记录。
3. **真实数据部署**：Phase 0 确定用 Dify Cloud + 合成数据；真实数据要在 Dify Cloud 与独立自部署之间另选，当前不预设已经获准。
4. **历史记忆范围**：建议首期只用当前模板 + 非正文使用统计。若希望读取历史日记或保存长期接受/拒绝偏好，需要 `LN-008` 的派生数据、删除和备份设计，不并入首期。
5. **Phase 3 产品边界**：实现前需要明确批准更新 `product.md`、`DESIGN.md` 和正式页面规范；本方案文档不会悄悄覆盖现有“Agent 仅可选择已有分类”的规则。
